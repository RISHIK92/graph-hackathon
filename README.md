# Nodus: a company brain on FalkorDB

**Track entered: Track 03, Company Brain**

Nodus is an organizational intelligence engine built on FalkorDB. It unifies fragmented company state—people, teams, systems, projects, tickets, documents, chats, and architectural decisions—into a single bi-temporal knowledge graph. Rather than relying on probabilistic RAG retrieval over flat text chunks, Nodus models facts as versioned graph assertions backed by exact source spans. It answers "who owns this?", "who knows about this?", and "why was this decided?" with deterministic provenance, and executes permission-guarded workflows directly inside FalkorDB.

* **Demo video:** https://youtu.be/8PCFA0UFk5s

* **Live deployment:** https://nodus.rishiklabs.tech/

* **Blog:** https://dev.to/rishik92/every-fact-cited-dated-and-disputed-building-nodus-on-falkordb-14

The demo company is fully synthetic, generated by `world/build.py` and committed under `world/seeds/`. No private or personal data is used.

## How Nodus covers the Track 3 focus areas

**Unified ingestion across docs, tickets, and chats.**

* Multi-format connectors normalize design docs, issue tickets, Markdown files, and Slack exports into a uniform provenance subgraph: `Source` nodes segmented into quotable `Span`s that `MENTION` domain `Entity` nodes.

* Extracted claims are materialized as `Assertion` nodes linked directly to the exact character offsets in the `Span` that evidenced them.

**Hierarchical ownership and multi-signal expertise resolution.**

* Ownership is resolved via a deterministic fallback traversal: direct `OWNS` edges, the owning team's `LEADS`, structural inheritance across `PART_OF` project hierarchies, and historical ownership if no active claim exists.

* Expertise is computed by aggregating weighted graph signals: authored documentation spans, system ownership, team leadership, project contributions, ticket assignments, and architectural decision authorship.

**End-to-end decision lineage.**

* Every `Decision` (ADR) connects to its motivating context (`MOTIVATED_BY -> Span`), decision-makers (`DECIDED_BY -> Person`), and blast radius (`AFFECTS -> Entity`).

* `REPLACES` chains track architectural evolution over time, allowing queries like "why did we adopt ADR-007?" to traverse both current rationale and overturned predecessors.

**Bi-temporal state and conflict resolution.**

* Every assertion tracks two time dimensions: *valid time* (`valid_from` / `valid_to`, when the fact was true in reality) and *transaction time* (`recorded_at` / `retracted_at`, when the brain learned or retracted it).

* Authority-weighted state transitions handle contradictions automatically: newer claims of equal or higher authority `SUPERSEDE` prior assertions, while lower-authority contradictions (e.g., an informal Slack message contradicting an official ADR) are flagged as `DISPUTES` without overwriting current truth. Nothing is ever deleted.

* Point-in-time queries reconstruct either actual historical state or the system's belief state at any past timestamp.

* Stale documentation detection cross-references latest document revisions against superseded assertions to flag outdated wiki pages automatically.

**Deterministic verification and zero-hallucination citations.**

* Every claim in a response is bound to its underlying `Assertion` and source `Span`.

* Before an answer is returned, a deterministic verifier validates every claim against FalkorDB—checking assertion existence, exact quote bounds, temporal validity (past vs. present tense), and explicit labeling of disputed or proposed states.

* If the graph lacks verified evidence, Nodus explicitly reports what is missing rather than extrapolating.

**Transactional graph actions with in-database RBAC.**

* Operational workflows—routing tickets, drafting superseding ADRs, confirming or resolving disputed facts, and rolling back actions—execute as single atomic Cypher transactions.

* Authorization is enforced directly by the organizational graph (e.g., verifying the actor `LEADS` the currently owning `Team`) inside the write query itself. Unauthorized mutations abort atomically.

* Pending proposals emit events to configurable webhooks.

## FalkorDB features used

| Feature | How Nodus uses it |
| --- | --- |
| Vector index (`db.idx.vector.queryNodes`, `vecf32`) | Embeddings on `Entity` and `Span` nodes for semantic retrieval |
| Full-text index (`db.idx.fulltext.queryNodes`) | Keyword retrieval, combined with vector results and graph expansion |
| `algo.pageRank`, `algo.betweenness`, `algo.WCC`, `algo.SPpaths` | Org-wide analytics on point-in-time snapshot graphs |
| `GRAPH.CONSTRAINT CREATE ... UNIQUE` | Sentinel guard that aborts unauthorized writes |
| `GRAPH.COPY` | Per-user workspaces cloned from `nodus_demo_template`; checkpoints saved as `<ws>__cp_<name>` |
| `GRAPH.RO_QUERY` + `GRAPH.CONFIG SET TIMEOUT` | Read-only, time-limited queries for the UI, MCP tools and verifier |

## Graph data model & FalkorDB architecture

```
graph LR
  Source -- HAS_SPAN --> Span
  Span -- MENTIONS --> Entity
  Span -- AUTHORED_BY --> Person
  Assertion -- EVIDENCED_BY --> Span
  Assertion -- "SUPERSEDES / CONTINUES / DISPUTES / CONFIRMS" --> Assertion
  Decision -- MOTIVATED_BY --> Span
  Action -- BASED_ON --> Assertion
  Action -- PRODUCED --> Assertion
  Action -- TARGETS --> Entity

```

**Dual-layer storage design:**
Nodus separates the **Assertion Ledger** (immutable provenance and bi-temporal history) from the **Entity Relationship Cache** (high-speed operational edges).

1. **Entities** (all carry the base `Entity` label for indexed lookup plus a domain label): `Person`, `Team`, `System`, `Project`, `Decision`, `Ticket`.

2. **Materialized Entity Edges:**

| Relationship | Meaning | 
| ----- | ----- | 
| `Team -OWNS-> System / Project` | Direct operational ownership | 
| `Person -LEADS-> Team` | Team leadership and approval authority | 
| `Person -MEMBER_OF {primary}-> Team` | Organizational membership | 
| `Person -WORKS_ON-> Project` | Active project contribution | 
| `System -PART_OF-> Project` | Structural hierarchy for inherited ownership | 
| `System -DEPENDS_ON-> System` | Service topology and failure blast radius | 
| `Ticket -ABOUT-> Entity`, `Ticket -ASSIGNED_TO-> Person` | Operational work tracking | 
| `Decision -AFFECTS-> Entity`, `-DECIDED_BY-> Person`, `-REPLACES-> Decision` | Architectural governance | 

Every materialized edge carries `aid` (pointer to the backing `Assertion`), `valid_from`, `valid_to`, and `authority`. This allows standard operational traversals to run in sub-millisecond time over sparse matrices without scanning historical assertion chains.

**Provenance and temporal ledger:**

* **`Source`**: A versioned document, ticket, chat log, or file upload (`doc_key`, `is_latest`, `updated_at`).

* **`Span`**: An immutable, quotable segment of a source with character bounds, timestamp, and author link.

* **`Assertion`**: An atomic claim (`predicate`, `subject_id`, `object_id` / `object_value`, `valid_from` / `valid_to`, `recorded_at` / `retracted_at`, `status` IN `[current, superseded, disputed, retracted, proposed]`, `authority`). Assertions sharing a subject-predicate key form a linked `Chain`.

* **`EVIDENCED_BY`**: Connects assertions to spans and encodes epistemic authority: structured field / human confirmation = `4`, documentation prose = `2`, chat message = `1`, unconfirmed agent draft = `0`. Rank `0` is retained for auditability but excluded from citation queries.

* **`Action`**: An audit node recording mutations (`BASED_ON -> Assertion`, `PRODUCED -> Assertion`), enabling deterministic action explanations (state *then* vs. state *now*) and clean transactional rollbacks.

**Temporal snapshot projections for FalkorDB `algo.*`:**
FalkorDB's native graph algorithms (`algo.pageRank`, `algo.betweenness`, `algo.WCC`, `algo.SPpaths`) operate at the C/GraphBLAS layer and filter strictly by node label and relationship type, rather than evaluating dynamic Cypher property predicates (`valid_from <= $V < valid_to`) per hop. To run structural algorithms at arbitrary points in time without polluting the primary graph, Nodus materializes lightweight, read-only temporal snapshot graphs (`<graph>__snap_<YYYYMMDD>`). Each snapshot projects only the edges valid at that timestamp, alongside pre-aggregated `TOUCHES {w}` authorship edges and undirected `LINK` topology edges. Analytical rankings are computed on the snapshot, while every surfaced claim is joined back to the primary graph for citation verification.

## System architecture & integrations

```
sources ──connectors──▶ Source ─HAS_SPAN─▶ Span ─MENTIONS─▶ Entity
                                            ▲
            candidates ──write path──▶ Assertion ─EVIDENCED_BY┘
                                   │   SUPERSEDES / CONTINUES / DISPUTES (timestamped, never deleted)
                                   └─▶ entity edges (OWNS, LEADS, DEPENDS_ON, …) = current-belief cache
question ─▶ plan ─▶ Cypher tools ─▶ evidence ─▶ claims ─▶ verifier ─▶ cited answer (or "here's what's missing")
action   ─▶ write tool ─▶ one guarded query (permission check + Action node) ─▶ explain_action (then / now)

```

* **Graph-first determinism:** FalkorDB is the sole arbiter of truth. LLMs (via OpenRouter) are strictly optional and used only for unstructured candidate extraction, query planning, and natural-language phrasing. Without an API key, Nodus runs 100% offline using a deterministic pattern extractor, rule-based query planner, and local embeddings.

* **Model Context Protocol (MCP) Server:** Exposes the graph's read, analytical, and guarded-write primitives over `stdio` or HTTP (`mcp_server.server`), allowing coding agents (Claude Code, Cursor, custom MCP clients) to query system ownership, trace blast radii, and propose architectural changes directly from the IDE.

* **FastAPI Backend & Ingestion CLI:** Provides REST endpoints for chat, temporal graph exploration, administrative file ingestion (`POST /admin/upload`), and outbound webhook notifications (`BRAIN_PENDING_WEBHOOK`) when new disputes or proposals require team lead approval.

## Cypher queries and graph algorithms

All graph interactions use parameterized Cypher templates backed by integration tests.

**Direct ownership at valid time `$V`** (`owner_at`):

```
MATCH (owner:Entity)-[o:OWNS]->(x:Entity {id:$x})
WHERE o.valid_from <= $V AND o.valid_to > $V
RETURN owner.id AS owner, owner.name AS name, o.aid AS aid, o.valid_from AS vf, o.valid_to AS vt, o.authority AS authority

```

**Inherited ownership via project hierarchy** (`owner_inherited`):

```
MATCH (x:Entity {id:$x})-[pp:PART_OF]->(p:Entity)
WHERE pp.valid_from <= $V AND pp.valid_to > $V
WITH p, pp
MATCH (owner:Entity)-[o:OWNS]->(p)
WHERE o.valid_from <= $V AND o.valid_to > $V
RETURN owner.id AS owner, owner.name AS name, o.aid AS aid, o.valid_from AS vf, o.valid_to AS vt,
       o.authority AS authority, p.id AS via, p.name AS via_name, pp.aid AS via_aid

```

**Multi-signal expertise aggregation** (`experts_signals`):

```
MATCH (x:Entity {id:$x})
OPTIONAL MATCH (x)<-[:MENTIONS]-(s:Span)-[:AUTHORED_BY]->(p:Person)
WHERE s.ts <= $V
WITH x, collect({person:p.id, kind:'authored', ref:s.id, ts:s.ts}) AS authored
OPTIONAL MATCH (x)<-[r:OWNS|WORKS_ON|LEADS]-(p2:Person)
WHERE r.valid_from <= $V AND r.valid_to > $V
WITH x, authored, collect({person:p2.id, kind:type(r), ref:r.aid, ts:r.valid_from}) AS direct
OPTIONAL MATCH (x)<-[o:OWNS]-(t:Team)<-[l:LEADS]-(p3:Person)
WHERE o.valid_from <= $V AND o.valid_to > $V AND l.valid_from <= $V AND l.valid_to > $V
WITH x, authored, direct, collect({person:p3.id, kind:'LEADS', ref:l.aid, ts:l.valid_from}) AS leads
OPTIONAL MATCH (x)<-[ab:ABOUT]-(k:Ticket)-[asg:ASSIGNED_TO]->(p4:Person)
WHERE ab.valid_to > $V AND asg.valid_from <= $V AND asg.valid_to > $V
WITH x, authored, direct, leads, collect({person:p4.id, kind:'ASSIGNED_TO', ref:asg.aid, ts:asg.valid_from}) AS tickets
OPTIONAL MATCH (x)<-[af:AFFECTS]-(d:Decision)-[db:DECIDED_BY]->(p5:Person)
RETURN authored, direct, leads, tickets,
       collect(CASE WHEN af.valid_to > $V AND db.valid_to > $V
               THEN {person:p5.id, kind:'DECIDED_BY', ref:db.aid, ts:db.valid_from} END) AS decided

```

**Decision lineage and rationale traversal** (`decision_trace`):

```
MATCH (d:Decision {id:$d})
OPTIONAL MATCH chain = (d)-[:REPLACES*0..5]->(old:Decision)
WITH d, collect(DISTINCT old.id) AS replaced
OPTIONAL MATCH (d)-[db:DECIDED_BY]->(who:Entity)
WITH d, replaced, collect(DISTINCT CASE WHEN db.valid_from <= $V AND db.valid_to > $V
                                   THEN {id:who.id, name:who.name, aid:db.aid} END) AS deciders
OPTIONAL MATCH (d)-[af:AFFECTS]->(x:Entity) WHERE af.valid_from <= $V AND af.valid_to > $V
WITH d, replaced, deciders, collect(DISTINCT {id:x.id, name:x.name, aid:af.aid}) AS affects
OPTIONAL MATCH (d)-[m:MOTIVATED_BY]->(s:Span) WHERE m.recorded_at <= $T AND m.removed_at > $T
RETURN d.id AS id, d.name AS name, d.title AS title, d.decided_at AS decided_at, d.status AS status,
       d.status_aid AS status_aid,
       replaced, deciders, affects, collect(DISTINCT {span:s.id, section:m.section, action_id:m.action_id}) AS motivated

```

**Strict evidence resolution** (`evidence_fragment` — filters out unconfirmed drafts, agent-generated text, and evidence not yet recorded at transaction time `$T`):

```
UNWIND $aids AS aid
MATCH (a:Assertion {id:aid})
WITH a, [(a)-[ev:EVIDENCED_BY]->(s) WHERE ev.authority >= 1 AND ev.recorded_at <= $T AND ev.removed_at > $T
          AND s.kind <> 'draft' AND s.author_role <> 'agent'
          | {span:s.id, form:ev.form, authority:ev.authority, qs:ev.quote_start, qe:ev.quote_end, src:ev.source_id}] AS evs
RETURN a.id AS aid, evs

```

**Stale documentation detection** (`stale_detection` — finds latest documents still asserting facts that were superseded after the document's last update):

```
MATCH (src:Source)-[h:HAS_SPAN]->(s:Span)<-[e:EVIDENCED_BY]-(a:Assertion)
WHERE src.is_latest = true AND src.kind <> 'confirmation' AND src.kind <> 'draft'
  AND h.removed_at = $max AND e.removed_at = $max AND e.authority >= 1
  AND (a.status = 'superseded' OR a.status = 'retracted') AND a.valid_to > src.updated_at
  AND ($e = '' OR a.subject_id = $e OR a.object_id = $e)
RETURN DISTINCT s.id AS span, src.id AS source, src.doc_key AS doc_key, src.title AS title,
       a.id AS aid, a.statement AS statement, a.subject_id AS s, a.object_id AS o, a.predicate AS p,
       a.valid_to AS valid_to, a.chain_id AS chain, 'stale' AS why

```

**Upstream/downstream blast radius** (`impact_dependents` — bounded variable-length path traversal where every hop satisfies temporal validity):

```
MATCH p = (x:Entity {id:$x})<-[:DEPENDS_ON*1..3]-(s:Entity)
WHERE all(e IN relationships(p) WHERE e.valid_from <= $V AND e.valid_to > $V)
RETURN s.id AS id, s.name AS name, s.tier AS tier, length(p) AS hops,
       [n IN nodes(p) | n.id] AS node_ids, [e IN relationships(p) | e.aid] AS aids
ORDER BY hops ASC, tier ASC
LIMIT 20

```

### Graph algorithms (executed on temporal snapshots)

Nodus leverages FalkorDB's native graph algorithms over point-in-time snapshot projections to surface structural risks that local neighborhood traversals miss:

| Organizational Question | FalkorDB Procedure | Graph Mechanics & Interpretation | 
| ----- | ----- | ----- | 
| **Which systems are most critical?** | `algo.pageRank('System', 'DEPENDS_ON')` | Computes transitive dependency centrality across `System` nodes. Systems depended on by many high-tier services rank highest. | 
| **How is X connected to Y?** | `algo.SPpaths` | Finds the top-3 shortest paths (up to 4 hops, bidirectional) connecting any two people, teams, or systems. | 
| **Who are our single points of failure?** | `algo.betweenness` | Measures bridge centrality across undirected `LINK` edges (`Person`, `Team`, `System`) to identify individuals who bottleneck cross-team knowledge flow. | 
| **Where are our knowledge gaps / silos?** | `algo.WCC` | Computes Weakly Connected Components over `OWNS`, `LEADS`, `MEMBER_OF`, and `PART_OF` to isolate orphaned systems and disconnected organizational islands. | 

```
CALL algo.betweenness({nodeLabels: ['Person', 'Team', 'System'],
                       relationshipTypes: ['LINK'],
                       samplingSize: $n, samplingSeed: $seed}) YIELD node, score
WITH node, score
WHERE 'Person' IN labels(node)
RETURN node.id AS id, node.name AS name, score

```

```
CALL algo.WCC({nodeLabels: ['Person', 'Team', 'System', 'Project'],
               relationshipTypes: ['OWNS', 'LEADS', 'MEMBER_OF', 'PART_OF']}) YIELD node, componentId
RETURN node.id AS id, node.name AS name, labels(node) AS labels, componentId AS c

```

Algorithm outputs are treated as structural rankings rather than standalone claims; Nodus automatically resolves the underlying edges back to the main graph so every surfaced path or score is accompanied by cited assertions.

### Atomic guarded writes in FalkorDB

To prevent time-of-check to time-of-use (TOCTOU) race conditions between application code and database state, every mutation in Nodus is compiled into a **single atomic Cypher query**. Each write query opens with an in-graph authorization and state-precondition stage. If the actor lacks org-graph permission or the target assertion has already been superseded, the query triggers a deliberate unique-constraint violation on a sentinel node (`:GuardFail {id:'sentinel'}`), forcing FalkorDB to roll back the entire transaction cleanly:

```
FOREACH (_ IN CASE WHEN ok THEN [] ELSE [1] END | CREATE (:GuardFail {id:'sentinel'}))

```

This guarantees that permission verification, assertion state transitions, materialized cache updates, and `Action` audit logging succeed or fail as one indivisible unit.
